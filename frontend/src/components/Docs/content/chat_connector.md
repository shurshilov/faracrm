**Коннектор** — это подключённый канал связи с клиентами: Telegram, Avito, ВКонтакте, MAX (МАКС), WhatsApp, электронная почта, телефония. Каждый коннектор описывает «как принимать и отправлять сообщения по этому каналу». Настраивается в разделе «Настройки → Коннекторы».

## Поддерживаемые каналы

- **Telegram** — бот (Bot API).
- **Avito** — переписка по объявлениям.
- **ВКонтакте** — сообщения сообщества (Callback API).
- **MAX (МАКС)** — три варианта: бот, агрегатор WAMM, официальный бизнес-API.
- **WhatsApp** — отправка по номеру.
- **Email** — SMTP (отправка) + IMAP (приём).
- **Телефония** — звонки (модуль телефонии).

## Как обрабатываются входящие

Когда клиент пишет вам, происходит цепочка (единая для всех каналов):

1. **Приём.** Внешний сервис шлёт **вебхук** на адрес FARA (у каждого коннектора свой). Для почты — периодический опрос IMAP.
2. **Определение коннектора.** Система понимает, к какому именно коннектору относится сообщение (по идентификатору канала / номеру).
3. **Поиск клиента.** По контакту отправителя (номер телефона, id в мессенджере) ищется **партнёр**. Сопоставление идёт по контактам с учётом формата телефона (см. ниже).
4. **Создание, если нужно.** Если клиента нет — создаётся партнёр, при необходимости **лид**, и открывается чат, привязанный к ним.
5. **Доставка операторам.** Сообщение появляется в разделе «Общение» у ответственных сотрудников — вживую (без перезагрузки) и с уведомлением.

> [!info] Один входящий диалог = один чат «записи», связанный с партнёром/лидом. Вся история в одном месте, вложения клиента сохраняются в хранилище так же, как файлы из внутренних чатов.

## Сопоставление контакта и коннектора

Чтобы верно «узнать» клиента и выбрать правильный канал ответа, используется тип контакта. Часть каналов работает по **номеру телефона** (телефон нормализуется — учитывается формат), часть — по внутреннему **id** пользователя канала (например, бот MAX). Поэтому у партнёра стоит указывать контакты в правильных типах (телефон, email, id мессенджера) — тогда входящее уверенно привяжется к нужной карточке.

## Написать клиенту первым

Для каналов, которые это позволяют (WhatsApp, бизнес-MAX и т.п.), доступна **отправка по номеру**: вы инициируете диалог, указав номер, и система сама заведёт/подберёт партнёра, лид и чат. Связь с внешним диалогом сохраняется, поэтому ответ клиента попадёт в тот же чат, а не «разъедется» в новый.

## Правила маршрутизации в лиды

Можно настроить правила, по которым новый входящий диалог автоматически порождает лид с нужной командой/стадией. Это удобно, чтобы обращения из разных каналов сразу попадали в правильную воронку.

## Проверка почтового коннектора

У email-коннектора есть кнопка **«Проверить соединение»** — она отдельно проверяет доступ по SMTP (отправка) и IMAP (приём), чтобы не гадать, почему письма не ходят.

> [!warning] Для каждого канала нужен свой доступ: токен бота, ключ сообщества, логин/пароль приложения для почты и т.д. Заводите их в настройках коннектора и держите в секрете — это доступ к переписке.

## Телефония

Телефонные коннекторы (Asterisk / FreePBX, Sipuni, МегаФон ВАТС) устроены одинаково: события звонков провайдер шлёт на **вебхук** FARA, а историю, записи разговоров и список номеров FARA забирает из его API. Звонок попадает в отдельный реестр — раздел **«Звонки»**, и подмешивается в чат с клиентом.

### Синхронизация номеров

Кнопка **«Синхронизировать номера»** подтягивает от провайдера внутренние номера (extensions), транки, группы и очереди в раздел **«Номера»**. Если у сотрудника есть контакт с таким же значением — номер привязывается к нему. Тип контакта не важен: подойдёт и **SIP** (обычно так заводят extension в Asterisk), и обычный **телефон**; главное — совпадение значения. Привязка нужна, чтобы карточка разговора показывалась именно тому, кто снял трубку.

> [!warning] Это обязательный шаг настройки. По списку своих номеров система определяет направление звонка (входящий/исходящий), нашу линию и оператора, а также отличает внутренние звонки сотрудник↔сотрудник от клиентских. Без синхронизации звонки будут писаться без этих данных.

### История звонков

Кнопка **«Прочитать историю»** импортирует звонки за выбранный период. Режим импорта выбирается рядом:

- **Без уведомлений и без лидов** (по умолчанию) — просто пополнить реестр звонков;
- **Без уведомлений** — с лидогенерацией, но без всплывающих карточек;
- **Обычный** — как живые звонки: карточка оператору и лид.

Повторный импорт безопасен — дубли гасятся по идентификатору звонка. Есть и фоновая cron-задача с тем же импортом (по умолчанию выключена, включается в списке задач), плюс задача периодической синхронизации номеров.

### Проверка соединения

Кнопка **«Проверить соединение»** запрашивает у провайдера список номеров — так сразу видно, верны ли адрес и доступы.

## Asterisk / FreePBX

Рядом с АТС ставится внешний **Asterisk-agent**: он отправляет события ARI на вебхук FARA, а историю (CDR), записи и номера FARA берёт из его REST API по логину и паролю (Basic-auth).

В коннекторе задаются **URL Asterisk-agent**, **логин** и **пароль**, а адрес вебхука со вкладки «Webhooks» указывается в конфиге агента как адрес отправки ARI-событий.

Раздел **«События»** — журнал телефонии: видно, какие ARI-события пришли и какие чтения истории выполнялись, без доступа к серверу АТС.

## Sipuni

Логин и пароль из личного кабинета Sipuni (поля «Логин»/«Пароль»), адрес API по умолчанию `https://sipuni.com/api`. Адрес вебхука со вкладки «Webhooks» указывается в интеграциях личного кабинета Sipuni — API его не устанавливает.

## МегаФон ВАТС

В коннекторе задаются адрес API `https://<домен>/crmapi/v1`, **API-ключ** (уходит в заголовке `X-API-KEY`) и **CRM-токен** — им проверяются входящие вебхуки. Адрес вебхука указывается в личном кабинете ВАТС.

## Звонки из CRM: софтфон в браузере

Если у коннектора Asterisk заполнена вкладка **«Авторизация»**, в шапке появляется иконка телефона: набор номера, поиск по телефонным контактам клиентов и сотрудников, приём входящих. Разговор идёт прямо в браузере, отдельная программа не нужна.

Чтобы включить, нужно две вещи:

1. На вкладке **«Авторизация»** коннектора — **адрес веб-сокета АТС** (например `ws://192.168.1.10:8088/ws`) и **SIP-домен**.
2. У линии сотрудника в разделе **«Номера»** — **пароль SIP**. Пароль не читается обратно: он уходит только владельцу линии в момент регистрации.

Пусто — иконки нет, ничего не грузится. Звонилка ни на что не влияет: история звонков, записи, лиды и всплывающая карточка приходят от АТС и работают независимо от неё.

### Как работает регистрация

**Внутренний номер — это не телефон. Это запись в справочнике АТС: «где сейчас искать сотрудника 201».**

Когда софтфон запускается, он говорит АТС: «я 201, вот пароль, ищи меня по адресу 192.168.1.50». АТС сохраняет этот адрес — он называется **контакт** и живёт недолго, поэтому телефон каждые пару минут повторяет «я всё ещё здесь». Когда кто-то набирает 201, АТС берёт адрес из справочника и звонит по нему.

Сколько адресов помещается в одну запись, задаёт параметр **Max Contacts** на внутреннем номере. По умолчанию — **один**.

### Два устройства на одном номере

Например, MicroSIP на двух телефонах у одного сотрудника. Так можно, но с оговорками:

- при `Max Contacts = 1` второй софтфон **вытеснит первый** из справочника (первый об этом не узнает и просто перестанет получать звонки) либо сам получит отказ;
- при `Max Contacts = 2` зарегистрируются оба, но штатный набор FreePBX `Dial(PJSIP/201)` зазвонит **только на том, что регистрировался последним**. Чтобы звонили оба, в диалплане нужен `Dial(${PJSIP_DIAL_CONTACTS(201)})`.

### Браузер рядом с обычной трубкой

У браузера добавляется вторая причина, посерьёзнее. WebRTC обязывает шифровать звук (**DTLS-SRTP**), и это требование самого браузера, а не CRM. А шифрование включается **на внутреннем номере целиком** — сразу для всех устройств на нём. Обычная настольная трубка или MicroSIP так не умеют и на такой номер просто не зарегистрируются.

Отсюда правило:

| Ситуация | Что делать |
|---|---|
| Сотрудник говорит **только из CRM** | Включить WebRTC на его обычном номере. Второй номер не нужен |
| У сотрудника **есть трубка или MicroSIP** | Завести **отдельный** внутренний номер под браузер (например 2201 при столе 201) |

Во втором случае добавьте сотруднику контакт со значением нового номера и нажмите «Синхронизировать номера» — обе линии привяжутся к нему, и звонки с любой попадут в его историю.

### Как браузер соединяется с АТС

Соединение идёт **через саму CRM**. Браузер подключается к CRM, а она пересылает служебные сообщения на АТС по адресу из настроек коннектора. Ничего в конфигурации сервера настраивать не нужно — только заполнить поле в интерфейсе.

Так сделано по трём причинам: браузеру запрещено открывать соединение на чужой домен (политика безопасности CRM), переиспользуется уже действующий сертификат CRM — на АТС свой не нужен, и **АТС вообще не нужно выставлять в интернет**: до неё достаточно доступа с сервера CRM по внутренней сети.

> [!warning] **Звук идёт мимо CRM.** Проксируется только служебный обмен; сам разговор передаётся напрямую между браузером и АТС. Поэтому UDP-порты 10000–20000 с АТС наружу нужны в любом случае, а если АТС не имеет внешнего адреса — звонки из браузера работать не будут без отдельного сервера ретрансляции (TURN).

### Что нужно на стороне АТС

- Веб-сокет АТС включён (обычно порт 8088) и доступен **с сервера CRM**. Наружу его открывать не нужно.
- Наружу открыты **UDP 10000–20000** — по ним идёт звук, он передаётся мимо CRM.
- На внутреннем номере: **Enable AVPF**, **ICE Support**, **rtcp Mux**, **Media Encryption = DTLS-SRTP**.
- Сама CRM должна открываться по **https** — иначе браузер не даст доступ к микрофону.

> [!warning] Если иконка телефона серая — браузер не смог зарегистрироваться на АТС. Проверьте по порядку: верен ли адрес веб-сокета АТС в коннекторе, отвечает ли АТС по этому адресу **с сервера CRM**, задан ли пароль SIP у линии сотрудника.
